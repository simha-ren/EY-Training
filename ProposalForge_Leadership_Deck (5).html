Chapter One · The Problem47 min lost · 12 tabs

Jack needs one answer.
The answer lives in ten places.

Every morning Jack reads proposals, RFCs and policy documents by hand, jumping between systems that were never designed to talk to each other. When he asks a generic AI chatbot to help, it answers confidently and cites nothing — so he can't trust it, and starts reading all over again.

Why today's approach fails Jack

Reading everything by hand is slow and inconsistent — two people give two different answers to the same question. Ask a generic chatbot instead, and it answers confidently while inventing facts it can't point back to a source for. And pasting real documents into a public tool means sensitive data walks out the door — a non-starter in regulated work.

What Jack actually needs

"What if one place just… knew?"

One question in. One trusted answer out — grounded in his own documents, cited so he can check it, and back in seconds.

Chapter Two · Market & Opportunity

Jack isn't one person. He's every document-heavy team.

Wherever work means reading long, high-stakes documents under compliance pressure, grounded and auditable AI wins — and generic chatbots are banned. ProposalForge is built for exactly that gap, and it isn't locked to any fixed set of domains.

Grounded, cited answers with per-domain safety are the trusted middle path, and it's rarely done well. I built this to be vendor-neutral and genuinely domain-agnostic — point it at any corpus, in any field, and it reasons over it without a rebuild.

How we built with KiroSpec-Driven Development

One feature, built the disciplined way: the Compliance Matrix

We used Kiro's Spec-Driven Development — a 3-phase workflow — to build our compliance feature. Requirements are written in EARS form, then designed, then executed task-by-task with a Definition of Done.

📋 The Compliance / Requirements Traceability Matrix

Paste an RFP and your proposal. It extracts every requirement, then traces each to your response with a coverage status and the matching evidence — turning a manual, error-prone audit into one click.

Why it's a strong Kiro fit

Its core is deterministic — the same inputs always give the same matrix, and it needs no API key at all; an LLM only steps in to summarise the gaps in plain language. Every requirement gets a stable ID and an evidence trail, so it's auditable by design, not by afterthought.

System Architecture · The AgentsLangGraph

Five agents, each with one job to do well

I didn't want one giant model trying to do everything at once. So I gave the work to five focused agents, each responsible for a single part of the answer, coordinated by LangGraph — here's the order they actually run in, and what each one is doing.

Agent 01

The Router

Reads the question first and decides which domain and knowledge base it belongs to. If it isn't confident, it asks rather than guessing — it never silently picks the wrong corpus.

Agent 02

The Guardrails Agent

Checks every draft answer for sensitive data, low confidence, domain mismatches and missing disclaimers before it's allowed anywhere near Jack.

Agent 03

The Retrieval Agent

Searches across every document I've given it — in Pinecone, or locally when it needs to — and pulls back only the passages that are actually relevant to the question.

Agent 04

The Generation Agent

Writes the answer itself — but only from what the Retrieval Agent handed it, with a citation attached to every claim it makes.

Agent 05

The Suggestion Agent

Looks at what was just asked and proposes the next question worth asking — so Jack keeps moving instead of starting a new search from scratch.

Why I split it this way

Each agent is small enough to test on its own, and every one of them reports its own metrics, logs and trace — so nothing that happens inside is ever a black box to me.

Zero API keys? Every one of these agents still runs — the Retrieval and Generation agents simply fall back to their offline mode.

System Architecture · Failure ScenariosIt never goes dark

Every dependency has a backup plan

The worst case is a clearly-labelled offline answer — never an outage, never a leaked secret, never a silent wrong answer. Each fallback names the tool it drops to.

🔌 AI provider down

handled

Fails over Claude → Groq → offline extractive (grounded, TF-IDF based). Always answers; the mode is labelled.

🗄️ Vector search down

handled

Falls over Pinecone → faiss → TF-IDF in-process. Retrieval keeps working with no external dependency.

📄 Doc parsing limited

handled

If Azure Document Intelligence isn't configured, it drops to local extraction (pypdf / docx / pptx). Ingestion never stops.

🧭 Unclear question

handled

Low confidence → offer a domain chip; too weak → ask Jack. It never guesses from the wrong corpus.

🔒 Sensitive data

blocked

Guardrail detects PII/PHI — email, phone, IDs and more — and flags it before the answer is trusted.

📉 Weak answer

gated

RAGAS below threshold → FLAG for review, not APPROVE. In CI it blocks the deploy entirely.

The load test enforces the failure budget too — breach p95 or error-rate after deploy and the pipeline stops the release.

The load-test harness

I run Locust with a weighted mix — 6× health checks, 4× retrieval-only, 2× the full pipeline — to mirror what real traffic actually looks like. On top of that, RAGAS grades faithfulness, relevance and context-recall on every single run, entirely through the Claude/Groq client I already have — no heavyweight eval package to install. And because the budgets are environment-overridable, I can tune them per environment without touching a line of code.

CI output · per-endpoint gate
[threshold] GET /health p95= 12.4ms budget= 50ms OK [threshold] POST /api/v1/retrieve p95= 31.8ms budget= 50ms OK [threshold] POST /api/v1/pipeline p95=2841.0ms budget=5000ms OK ────────────────────────────────── ✓ all budgets met — release proceeds

A full LLM answer can't be milliseconds — generation takes time. Sub-second budgets cover health & search; the answer is p95 < 5s, reported with throughput.

Guardrails & Governance — Why & Where

The right check, at the right point

Each guardrail exists because a specific failure would be unacceptable in regulated work. Here's where each fires and why it must.

GuardrailFires atWhy it's needed — the risk it prevents
PII / PHI detectionOn the generated answerA leaked ID, email or health identifier is a compliance breach — caught at error severity before the answer is trusted.
Confidence floorAfter compositionA low-confidence answer shown as fact misleads the user; below the floor it's flagged, not asserted.
Domain matchAt routingAnswering from the wrong corpus is worse than no answer — a mismatch forces a confirm or a re-ask.
Policy disclaimerOn finance / health answersThis guidance legally needs a disclaimer; a missing one is blocked at error severity.
Query relevanceQuestion vs. retrieved contextLow overlap signals weak grounding — it warns before a hallucinated reply reaches the user.
RAGAS quality gateEnd of pipeline & in CIUngrounded output must never ship — it FLAGs at runtime and blocks the deploy in CI.

Governance stance: answers are grounded, sensitive data is protected, each domain enforces its own rules, and every action is logged — the four properties that make this fit for regulated use.

Defense in depth: logins use industry-standard password hashing with re-validated sessions; guardrails sit at generation; the audit trail sits underneath — no single layer is the only safeguard.

Chapter Eleven · Challenges, Fixes & Enhancements

What we hit, and how we hardened it

Challenges we fixed

Chat could dead-end. When Claude was unavailable the chat returned "unable to generate." Now it transparently falls back to a grounded extractive answer — the app always answers, and labels the mode.

Analytics were placeholders. Replaced hardcoded charts with real per-query accuracy, groundedness & confidence trends.

Azure WebSockets blank UI. Diagnosed the default-off WebSockets trap; now required & documented so first deploy just works.

Enhancements shipped & next

Compliance matrix added via Kiro SDD — RFP requirements traced to coverage & gaps, fully tested.

Accuracy scoring & suggestions — every turn scored; follow-up chips now submit directly.

Roadmap to production

Here's what I'd tackle next: move secrets into Azure Key Vault, wire up auto-alerts on error-rate and latency, and tighten the routing logic based on real usage once we're in pilot.

Value-Based Learnings

What building this taught us

Grounding beats fluency

In regulated work, a cited answer you can check beats an eloquent one you can't. Trust is the product.

Degrade, never fail

Giving every dependency a fallback turned reliability from a hope into a guarantee.

Specs make speed

Kiro's requirements → design → tasks felt slower up front and was faster overall — it kills rework.

Quality is a gate

Putting RAGAS & latency budgets in CI meant quality could never quietly regress.

Neutrality is leverage

Vendor-independence isn't just principled — it removes the biggest blocker to adoption.

Observability pays back

Per-run traces turned "why is this slow or wrong?" from an investigation into a glance.
